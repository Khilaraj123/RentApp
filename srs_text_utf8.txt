1. Introduction
1.1 Purpose
This document defines the Software Requirements Specification (SRS) and Software Architecture Document (SAD) for RentSpace, a modern, general-purpose rental marketplace that enables owners to list and lend items (vehicles, rooms, electronics, tools, cameras, apparel, party equipment, and more) and enables customers to discover, book, and pay for rentals. It specifies the functional and non-functional requirements, the architectural approach, the domain model, and the technology choices that will guide design, implementation, and testing.
1.2 Scope
RentSpace is a web-based platform built with ASP.NET Core MVC following Clean Architecture and Domain-Driven Design (DDD) principles. The platform supports the full rental lifecycle: listing creation, search and discovery, booking and availability management, payments and security deposits, messaging, notifications, reviews, dispute resolution, and administrative oversight. The system is designed to scale from a focused MVP to an extensible platform supporting dynamic pricing, AI-assisted features, and progressive web app (PWA) capabilities.

2. Overall Description
2.1 Product Perspective
RentSpace is a standalone, self-contained marketplace platform, comparable in spirit to Airbnb or Facebook Marketplace but generalized for renting almost any physical item. It is composed of a server-side ASP.NET Core MVC application exposing web UI and APIs, a relational data store, background job processing (Hangfire), and integrations with payment gateways, maps, and notification channels.
2.2 Architectural Style
The system follows Clean Architecture, organizing code into concentric layers (Domain, Application, Infrastructure, Presentation) with dependencies pointing inward, combined with DDD tactical patterns (aggregates, entities, value objects, domain events, repositories) to keep business rules isolated from frameworks and delivery mechanisms.

2.4 Operating Environment
Server: ASP.NET Core (cross-platform), deployable on Linux or Windows containers
Database: SQL Server (or PostgreSQL) via Entity Framework Core
Client: Responsive web (desktop and mobile browsers), installable as a PWA
Background processing: Hangfire with a persistent job store
Cloud/File storage: Object storage (e.g., Azure Blob Storage or S3-compatible)
2.5 Design and Implementation Constraints
Domain layer must have no dependency on ASP.NET Core, EF Core, or any infrastructure package
All monetary values represented via a Money value object (amount + currency) to avoid float rounding errors
Local payment gateways (eSewa, Khalti) required in addition to Stripe/credit card, reflecting a Nepal-aware market
Availability and booking conflict checks must be transactionally consistent to prevent double-booking
2.6 Assumptions and Dependencies
Third-party services (Stripe, eSewa, Khalti, mapping provider, email/SMS provider) are available and contractually accessible
Users have access to a modern browser or mobile device supporting PWA installation
Identity documents submitted for verification are reviewed by human admins, not fully automated at MVP stage

6. Non-Functional Requirements
6.1 Performance
Search queries should return results within 500ms at p95 for catalogs up to 1M listings (with indexing/caching)
Booking availability checks must complete within 200ms to support real-time UI feedback
6.2 Scalability
Stateless web layer to allow horizontal scaling behind a load balancer
Read-heavy search workloads offloaded to a dedicated search index (e.g., Elasticsearch) as usage grows
6.3 Security
All traffic served over HTTPS/TLS 1.2+
Role-based and resource-based authorization enforced at the Application layer
Sensitive data (identity documents, payment tokens) encrypted at rest
Input validation and output encoding to mitigate injection and XSS
6.4 Availability & Reliability
Target 99.9% uptime for core booking and payment flows
Idempotent payment processing to avoid double charges on retries
6.5 Usability
Responsive design supporting mobile, tablet, and desktop breakpoints
Accessible UI conforming to WCAG 2.1 AA where practical
6.6 Maintainability
Clean Architecture boundaries enforced via project references and architecture tests
Automated unit and integration test coverage for domain and application layers
6.7 Compliance
Payment processing aligned with PCI-DSS via certified gateways (no raw card data stored)
Data handling aligned with applicable data protection regulations for user PII and identity documents

7.2 Payment Status Lifecycle
Status
Meaning
Pending
Payment initiated, awaiting gateway confirmation
Paid
Payment successfully captured
Failed
Payment attempt failed
Refunded
Full amount returned to renter
PartiallyRefunded
A portion of the amount returned (e.g., after deposit deduction)
7.3 End-to-End Rental Flow
Renter searches and filters listings by category, location, price, and availability.
Renter selects a listing and submits a booking request with rental period and options.
System validates availability and quantity; raises BookingRequestedEvent.
Owner approves (or instant booking auto-confirms); raises BookingConfirmedEvent.
Renter completes payment (and deposit, if applicable); raises PaymentSucceededEvent.
Renter picks up the item (optionally verified via QR code); raises ItemPickedUpEvent.
Renter returns the item at end of rental period; raises ItemReturnedEvent.
Owner/system inspects the item; deposit is released or partially deducted.
Both parties submit reviews; booking is marked Completed.
